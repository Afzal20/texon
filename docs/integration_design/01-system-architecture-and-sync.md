# Odoo–Texon Integration Architecture, Consistency & Implementation Strategy

> **Source:** Generated by subagent `/root/integration_design` during Texon Odoo ERP adaptation planning.  
> **Status:** Proposed System Architecture & Integration Blueprint  

---

Design recommendation, with assumptions: use self-hosted Odoo Community as the authoritative ERP and retain Texon’s Next.js UI plus a reduced Django integration layer where they create a useful apparel workflow. This is a proposed architecture, not a claim about Texon’s current implementation. I could not inspect the repository within this delegated task. Pin a verified Odoo release and image digest before implementation; Odoo 20 is a provisional target until its distribution, addons and API contract are exercised.

**Architecture decisions**

| Area | Decision to include in the plan |
|---|---|
| Ownership | Odoo owns confirmed customers/vendors, SKU variants, stock movements, purchase/sales documents, BOMs, production orders and any selected accounting records. Texon owns interface preferences, integration commands, delivery tracking and derived read models. Apparel fields that affect ERP calculations belong in a versioned Odoo addon. |
| Existing ERP tables | Classify every Texon table as migrate-and-retire, projection, or independent domain data. Prevent two authoritative writers for the same quantity, price, invoice or production status. |
| Frontend | Use Texon for a focused apparel order/production view and buyer portal. Use Odoo-native screens for broad administrative functions initially. Rebuilding all Odoo screens creates a second large product. Revisit the UI choice after one complete workflow works. |
| Boundaries | Next.js → authenticated Django endpoints → durable command queue → a small, explicitly allowed Odoo addon API. Keep Odoo keys and arbitrary model/method selection off the browser. |
| Tenant isolation | Prefer a dedicated Odoo database per unrelated customer for the first deployment. Odoo companies represent legal entities within a customer; they are not automatically a SaaS tenant boundary. Derive the database/connection from trusted server configuration, not a user-provided header. |
| Permission model | A restricted Odoo service account does not automatically preserve the Texon end-user’s permissions. Django must authorize each requested business action. Odoo must independently restrict company and record access, and record the actor’s immutable external ID for audit. |
| Scope | First supported pilot: one customer, one legal company, one warehouse, defined base currency/localization, one apparel production route. International customer acquisition does not require implementing every country’s financial compliance. |

The official Odoo multi-company guidance requires deliberate company context, relational company checks and record rules; merely adding `company_id` is insufficient. [Odoo multi-company guidelines](https://www.odoo.com/documentation/19.0/developer/howtos/company.html)

**Cross-system consistency**

1. In a Django transaction, write the user’s command and an outbox row together. Give the command a stable operation UUID, tenant/company identity, schema version, canonical payload hash and expected business revision.
2. A worker delivers that UUID unchanged on every retry. An Odoo addon method checks authorization, company, expected state and payload before changing business records.
3. Store an Odoo command receipt with a unique operation key in the **same transaction** as the business action. Repeated key plus identical payload returns the recorded result. Reused key with a different payload is rejected. Concurrent duplicates must be handled through a tested unique-constraint/savepoint or retry strategy.
4. A timeout after Odoo commits is “outcome unknown,” not permission to create another document. Query/replay the original operation safely.
5. Commit a separate Odoo outbox event in the transaction that changes ERP state. Deliver with retry and acknowledgment; consume with an inbox deduplication key in Django.
6. Do not assume increasing event IDs or `write_date` form a perfect delivery cursor: concurrent transactions can commit out of order. Use explicit delivery records/acknowledgment and periodic authoritative reconciliation.
7. Expose pending, succeeded, rejected and reconciliation-needed states in Texon. Never show “stock updated” solely because a command was queued.
8. Use supported Odoo business actions and extensions. Do not update `stock.quant`, posted accounting rows or ERP tables directly through SQL.
9. Keep each Odoo business transition atomic inside one method. Multiple JSON-2 requests cannot share one SQL transaction. A multi-system business process needs compensating actions and an auditable state machine, not an alleged distributed transaction. [Odoo JSON-2 transaction behavior](https://www.odoo.com/documentation/19.0/developer/reference/external_api.html)

Use JSON-2 for a verified supported version. Avoid stale documentation claims that all legacy RPC disappears in Odoo 20: current master documentation distinguishes the database service removal from later removal of common/object services. [Current Odoo API documentation](https://www.odoo.com/documentation/master/developer/reference/external_api.html)

**Apparel modeling decisions**

- Map a style to a product template and a sellable style–color–size combination to a variant. Establish unique external mappings; do not identify variants by display names.
- Freeze the supported size/color combinations for approved orders. Define how an attribute change creates or archives variants without silently relinking historical transactions.
- Support a shared BOM with variant-specific components where suitable. Snapshot or revision-pin the approved material specification for each production order so a later edit does not silently change released work. Odoo documents consolidated BOMs with per-variant applicability; verify the selected release’s exact semantics. [Variant BOM documentation](https://www.odoo.com/documentation/19.0/applications/inventory_and_mrp/manufacturing/advanced_configuration/product_variants.html)
- Resolve fabric traceability explicitly: a supplier dye batch may contain several physical rolls. A practical proposed model is one tracked lot per roll, with an explicit dye-batch reference grouping those rolls. Partial consumption must preserve remaining roll quantity and traceability.
- Use one stock unit per fabric SKU. For the MVP, purchase and consume in compatible length units; record measured weight separately. Kilograms-to-meters depends on material width, GSM and actual measurement, so do not invent a universal UoM ratio. Odoo’s documented purchase conversion requires compatible categories. [Odoo units of measure](https://www.odoo.com/documentation/19.0/applications/inventory_and_mrp/inventory/product_management/configure/uom.html)
- Distinguish planned consumption, actual consumption, reusable offcuts, scrap and production loss. Define tolerances and approval rules.
- A quality failure must put goods into a non-shippable state/location. Confirm which quality features actually exist in the selected Community build; budget a small explicit addon if necessary.
- Handle partial production, backorders, substitutions, returns, rework and credit notes through normal ERP workflows.
- Keep cost estimates separate from actual costs. State whether taxes and draft invoices are demonstrated or production accounting is supported.

**Migration and cutover**

- Inventory existing models, APIs, tests, document states and external integrations first. Produce a mapping sheet with owner, transformation, required fields, external IDs and reconciliation rules.
- Import in dependency order: companies/UoM/currencies → partners → templates/variants → locations/lots/BOMs → approved opening balances and open documents.
- Keep closed historical records available read-only unless there is a specific validated reason to recreate them. Do not manufacture historical postings merely to make a demo look populated.
- Give every migration a run ID, deterministic external references, resumable batches, reject report and dry-run reconciliation.
- Freeze legacy writes during final cutover; migrate deltas, reconcile, then enable the new writer. Compare stock by product, roll/lot and location, open-order quantities, receivables/payables if included, and document counts.
- Rehearse restoration of both databases and Odoo attachments together. After new business postings occur, a rollback may require controlled reversal/forward correction; simply restoring an old database can lose legitimate transactions.

**15 acceptance scenarios for the implementer/tester**

1. Create one style with two colors and three sizes; six unique SKUs appear, with stable mappings after synchronization repeats.
2. Select a size/color-specific BOM; the production order uses exactly the approved components and quantities for that variant.
3. Receive two rolls from one dye batch, consume only part of one roll, and show the remaining length plus forward/backward traceability.
4. Attempt a kilogram-to-meter conversion without an approved measurement rule; the system rejects it clearly.
5. Confirm a production order with insufficient fabric; expose the shortage and required procurement without duplicating demand.
6. Complete production partially, scrap the approved loss, and create the correct residual/backorder quantities.
7. Fail a quality check; blocked goods cannot be shipped through either Texon or the allowed Odoo workflow.
8. Ship partially, receive a customer return, and reconcile returned stock and any selected credit workflow.
9. Deliver the same command concurrently ten times; exactly one ERP business effect and one logical command receipt result.
10. Force a timeout after Odoo commits; replay returns the original document/result and creates no duplicate.
11. Stop the worker and broker, resume them, and verify commands/events recover without missing or duplicated business effects.
12. Deliver events late and out of order; projections converge to authoritative Odoo state and show synchronization health.
13. Attempt cross-customer database access and cross-company record references; both are rejected server-side with no data leakage.
14. Migrate the same fixture twice, resume an interrupted batch, and reconcile identical record mappings, stock and open-document totals.
15. Rehearse deployment plus backup restoration; verify documents and attachments, audit history, integration receipts and reconciliation before reopening writes.

For the >200-commit requirement, propose independently reviewable work items with prerequisites, files/subsystems, implementation intent and acceptance evidence. Do not create filler commits or pretend planned commits have already happened. A meaningful commit should include its relevant test updates; avoid systematically splitting each implementation from its tests just to increase the count.
