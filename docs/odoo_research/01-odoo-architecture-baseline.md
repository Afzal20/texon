Recommended baseline: **Odoo 20.0 Community, self-hosted**, with small Texon-specific Odoo addons, an integration adapter in Django, and the existing Next.js UI. Treat this as an architectural recommendation; runtime compatibility remains an implementation gate.

**Edition/hosting decision**

| Choice | Planning consequence |
|---|---|
| Self-hosted CE | Good default for public demo and development without Enterprise subscription. Own operations, backups, upgrades and addon maintenance. Core has LGPL-3 licensing and public JSON-2 implementation. |
| Self-hosted Enterprise | Requires valid Enterprise subscription and permitted module access; can run custom Python addons. |
| Odoo.sh | Managed hosting for custom/community addons; requires an Enterprise subscription including Odoo.sh. Confirm project/client commercial terms and budget before adoption. |
| Odoo Online | Cannot run the custom Python addons required for the proposed atomic bridge methods. Its hosted external API requires the Custom plan; Standard/One App Free do not include external API access. |

Sources: [Odoo.sh project creation source](https://raw.githubusercontent.com/odoo/documentation/20.0/content/administration/odoo_sh/getting_started/create.rst); [JSON-2 reference source](https://raw.githubusercontent.com/odoo/documentation/20.0/content/developer/reference/external_api.rst). The commercial hosted API plan statement must not be misrepresented as CE lacking an API: [public CE JSON-2 controller](https://raw.githubusercontent.com/odoo/odoo/20.0/addons/rpc/controllers/json2.py) and [rpc manifest](https://raw.githubusercontent.com/odoo/odoo/20.0/addons/rpc/__manifest__.py) establish its presence.

**API/version constraints**

Use JSON-2, introduced in 19, via `POST /json/2/<model>/<method>`, server-side RPC-scoped bearer key and a dedicated restricted integration user. The actual 20 controller declares `auth='bearer'`, `bearer_scope='rpc'`, and `save_session=False`.

Current 20 docs distinguish legacy RPC services: the **db service was removed in 20**; **common/object are deprecated, scheduled for 22 / Online 21.1**. Do not repeat obsolete “all RPC removed in Odoo 20” guidance.

Each JSON-2 request is one SQL transaction. Separate calls are not atomic. Use one custom Odoo model method for each related business operation. Manual API-key docs cap duration at three months; implement rotation before expiry, and verify role-specific programmatic duration restrictions in the selected build. Never expose the key to Next.js/browser bundles. [20 API reference](https://raw.githubusercontent.com/odoo/documentation/20.0/content/developer/reference/external_api.rst)

**Critical integration design, recommendations rather than native capabilities**

1. **One authority per domain:** Odoo owns confirmed sales/purchases, physical stock movements, reservations, manufacturing and financial postings. Texon owns garment-specific collaboration/planning and UI projections. Retire competing Django stock/accounting mutations as domains move over.
2. **Reliable commands:** Django transaction creates the local request plus outbox entry; workers send a stable operation UUID. An Odoo addon validates, records a unique command receipt, performs the business operation and saves its result in the same transaction. Timeout after server commit retries the same UUID. A different payload with the same UUID is an error.
3. **Reconciliation:** Odoo event/outbox records and Django inbox deduplicate responses, include company and schema version, and update read projections. At-least-once delivery, explicit pending/failed status, bounded retries, dead-letter review and scheduled reconciliation. Do not claim distributed exactly-once delivery.
4. **Do not invent a stock API:** wrap Odoo workflow actions and handle returned wizards/backorders. Directly writing quantities, bypassing move workflows or calling SQL against Odoo tables creates valuation/reservation inconsistencies.
5. **Command authorization:** validate user/group, allowed company, record ownership, quantities, state and revision inside each public bridge method. RPC-callable public methods cannot trust their arguments; CRUD ACL checks do not automatically authorize every business action. Avoid blanket `sudo()`. [Security source](https://raw.githubusercontent.com/odoo/documentation/20.0/content/developer/reference/backend/security.rst)
6. **Company boundaries:** set `company_id`, `_check_company_auto`, appropriate relational `check_company`, record rules, correct `with_company()` and restricted allowed company context. Test API/direct RPC, not only filtered UI. Prefer separate deployment/database per unrelated customer initially; multi-company is not an automatic SaaS tenant boundary. [Multi-company source](https://raw.githubusercontent.com/odoo/documentation/20.0/content/developer/howtos/company.rst)

**Garment mapping and version pitfalls**

- Style → `product.template`; size/color combinations → `product.product` variants. Plan stable mappings and SKU uniqueness.
- BOM component applicability supports variants, with OR across values of the same attribute and AND across different attributes; components without restrictions apply to all variants. Immutable approved Texon tech-pack/BOM revisions need explicit design; do not silently change existing production orders when a style changes. [20 variant BOM source](https://raw.githubusercontent.com/odoo/documentation/20.0/content/applications/inventory_and_mrp/manufacturing/advanced_configuration/product_variants.rst)
- Fabric roll/batch → traceable `stock.lot`, with garment-specific shade, width, measured weight and inspection data added deliberately. Native lots support receipt, manufacture, delivery and traceability, but do not by themselves prove garment roll allocation logic. [Lots source](https://raw.githubusercontent.com/odoo/documentation/20.0/content/applications/inventory_and_mrp/inventory/product_management/product_tracking/lots.rst)
- UOM is a major version trap: current 20 source uses `relative_uom_id` and `relative_factor`; do not hardcode old `uom.category` APIs from older tutorials. Choose one primary stock unit and explicit measured secondary attributes. Never assume a universal kg↔metre conversion. Test decimal precision and rounding. [20 UOM source](https://raw.githubusercontent.com/odoo/odoo/20.0/addons/uom/models/uom_uom.py)
- Odoo CE MRP includes workorders/workcenters in its manifest; do not describe all work orders as Enterprise-only. Rich Shop Floor/Quality/PLM/Barcode functionality should be an optional edition/module verification gate. [MRP manifest](https://raw.githubusercontent.com/odoo/odoo/20.0/addons/mrp/__manifest__.py)
- Core subcontracting supports vendor-supplied, resupplied and dropshipped component workflows. Test one chosen workflow first; partial outsourced garment operations may require modeled intermediate products or additional design rather than assuming native subcontracting is arbitrary operation outsourcing. [Subcontracting source](https://raw.githubusercontent.com/odoo/documentation/20.0/content/applications/inventory_and_mrp/manufacturing/subcontracting.rst), [CE manifest](https://raw.githubusercontent.com/odoo/odoo/20.0/addons/mrp_subcontracting/__manifest__.py).

**License/validation gates**

CE source declares LGPL-3. The current 20 licensing documentation still contains “19” headings, so rely on selected source/addon licenses and current commercial contract rather than assuming a heading proves new terms. Enterprise code requires a valid subscription and cannot be copied into the public Texon repo. Evaluate each third-party addon separately. [License docs](https://www.odoo.com/documentation/19.0/legal/licenses.html)

Meaningful integration tests for the implementer: duplicate/reordered delivery, timeout after remote commit, concurrent same-command execution, changed payload reuse, expired-key recovery, cross-company direct API denial, negative stock/rounding, partial receipt/backorder, variant BOM correctness, raw-lot-to-finished-lot traceability, cancellation/return reconciliation, restore plus event replay. Test against the real pinned Odoo runtime, not mocks alone. No code executed or tests run during this research.
